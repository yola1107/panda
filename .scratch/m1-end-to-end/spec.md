# M1：端到端长连接链路

Status: ready-for-agent

## Problem Statement

业务开发者想在 Kratos 体系上开发长连接应用，例如游戏，但仓库目前只有 Kratos 脚手架和一个 HelloWorld 接口。
客户端无法建立长连接，没有 Gate 或 Node，也没有数字路由、Handler 注册或主动推送。
开发者只能自己从零拼接接入、转交和回推，并且在组合部署和分离部署之间维护两套实现。

## Solution

交付一条可运行的最小链路，客户端能经 TCP 或 WebSocket 入口连上 Gate：
- 先发登录请求完成认证；
- 之后发请求并收到应答，发通知，接收业务触发的主动推送；
- 心跳维持连接。

业务开发者在 proto 中为一个逻辑服务声明数字路由。生成器产出 Handler 接口、注册代码、Go 客户端调用和类型化推送分发代码，开发者只需实现 Handler，并显式组装 Gate 与 Node。
同一套业务实现既能组合在一个进程里运行，也能把 Gate 和 Node 分开部署，两者遵守同一契约。
示例应用和 Go 参考客户端演示每种交互各一次。

## User Stories

1. 作为业务开发者，我想以 proto service 标识一个逻辑服务，并声明其请求、通知、登录请求和主动推送，以便协议契约只有一份来源。
2. 作为业务开发者，我想为每个请求、通知和主动推送声明数字路由，以便客户端协议紧凑且编号明确。
3. 作为业务开发者，我想让不同逻辑服务使用相同的数字路由而互不影响，以便各自独立编号。
4. 作为业务开发者，我想在同一逻辑服务内出现重复编号时，生成阶段就报错，以便尽早发现冲突。
5. 作为业务开发者，我想得到生成的 Handler 接口，以便只写业务逻辑，不手写路由分发。
6. 作为业务开发者，我想用生成的注册代码把 Handler 注册到 Node，以便路由表和 proto 保持一致。
7. 作为业务开发者，我想在 Handler 中拿到可信的用户身份和会话，以便做业务鉴权。
8. 作为业务开发者，我想在登录 Handler 中决定是否放行，并指定绑定的用户，以便认证决策归 Node。
9. 作为业务开发者，我想在 Handler 中返回 Kratos 错误，并让客户端收到带 reason 的失败应答，以便沿用 Kratos 的错误习惯。
10. 作为业务开发者，我想从业务代码中按会话发起主动推送，以便不依赖客户端请求就能下发状态。
11. 作为业务开发者，我想处理通知而不必返回应答，以便客户端单向上报。
12. 作为业务开发者，我想在 Handler 中调用普通 Kratos 微服务，以便长连接业务复用已有能力。
13. 作为业务开发者，我想通过显式组装创建 Gate 和 Node 并交给 kratos.App 运行，以便沿用 Kratos 的生命周期，不引入自动装配容器。
14. 作为业务开发者，我想用同一份业务实现切换组合部署和分离部署，以便不维护两套代码。
15. 作为部署者，我想在配置中为每个逻辑服务指定 TCP 监听端口和 WebSocket 路径，以便入口和逻辑服务一一对应。
16. 作为部署者，我想让多个 WebSocket 路径共用一个端口，以便减少端口占用。
17. 作为部署者，我想为每个入口配置编码器，例如 Protobuf 或 JSON，以便适配不同客户端。
18. 作为部署者，我想为每个入口配置最大包长，默认 64 KiB，以便限制恶意或异常的大包。
19. 作为部署者，我想配置认证超时和空闲超时，以便及时回收无效连接。
20. 作为部署者，我想配置每条连接的发送队列上限，以便慢客户端拖不垮 Gate。
21. 作为部署者，我想在分离部署时让 Gate 通过 Kratos 服务发现找到 Node，以便沿用现有治理方式。
22. 作为部署者，我想在 Node 下线时让绑定到它的会话被断开，以便客户端重连到可用的 Node。
23. 作为客户端开发者，我想用 Go 参考客户端经 TCP 或 WebSocket 连接入口，以便验证框架。
24. 作为客户端开发者，我想用生成的 Go 客户端调用发请求并收到类型化应答，以便不手写编号和编解码。
25. 作为客户端开发者，我想收到类型化的主动推送回调，以便处理服务端下发的消息。
26. 作为客户端开发者，我想用 RequestID 关联请求和应答，以便同一连接上并发多个请求。
27. 作为客户端开发者，我想在认证前只允许发登录请求和心跳，并得到明确的拒绝或断开，以便理解连接状态。
28. 作为客户端开发者，我想定时发心跳并收到 Gate 的心跳回复，以便确认连接存活。
29. 作为客户端开发者，我想在浏览器环境下也能使用同一协议，以便不依赖 WebSocket ping/pong。
30. 作为框架维护者，我想让 Gate 只透传 payload、不认识业务消息，以便新增路由时不改 Gate。
31. 作为框架维护者，我想让组合部署走本地调用，同时经过和 RPC 相同的身份校验、中间件与错误契约，以便组合部署不获得额外权限。
32. 作为框架维护者，我想让分帧解码对任意输入都不 panic、不做无界分配，以便 Gate 能抵御畸形数据。
33. 作为框架维护者，我想让超出最大包长的连接被断开，以便内存使用有界。
34. 作为框架维护者，我想让发送队列满时断开连接而不静默丢消息，以便关键消息不悄悄丢失。
35. 作为框架维护者，我想让链路追踪从 Gate 开始，并覆盖转交给 Node 的调用，以便定位慢请求。
36. 作为框架维护者，我想让连接关闭时释放全部资源，并让相关 goroutine 退出，以便长期运行不泄漏。
37. 作为示例使用者，我想运行一个示例，覆盖登录、一次请求与应答、一次通知和一次业务触发的主动推送，以便快速理解框架用法。
38. 作为示例使用者，我想用同一个示例分别以组合部署和分离部署运行，以便看到两种部署的行为一致。
39. 作为业务开发者，我想在执行超时或连接关闭时通过 Handler 的 Context 收到取消，以便结束在途工作。
40. 作为部署者，我想限制每条连接和每个 Node 的在途执行数量，以便慢 Handler 或持续请求不会造成无界积压。

## Implementation Decisions

协议与架构决策见 [ADR 目录](../../docs/adr/) 中的 0001 至 0006，范围决策见 [设计讨论记录第八节](../../docs/design/long-connection-discussion.md#八文档规划会话的后续确认)。本规格不重复其细节，只列出要构建的模块：

- **客户端协议模块**：负责 [ADR 0004](../../docs/adr/0004-client-protocol-envelope.md) 定义的 13 字节固定头部信封和两种分帧，即 TCP 长度前缀和 WebSocket 二进制消息。它负责编解码和最大包长校验，不依赖 Gate 或 Node。
- **入口与传输**：TCP 监听和 WebSocket 路径。每个入口绑定一个逻辑服务、一个编码器和一组限制。两种传输向上提供同一种连接抽象，只保留各自的特有配置。
- **Gate**：
  - 管理连接生命周期：未认证、已认证、关闭。
  - 处理心跳、认证超时和空闲超时，维护有界发送队列。
  - 先选定 Node 再转交登录；分离部署经 Kratos 服务发现选定。认证成功且该次登录仍有效时才创建会话，会话此后的请求与通知固定发往该 Node。
  - 转交携带 [ADR 0006](../../docs/adr/0006-gate-node-internal-contract.md) 的连接上下文；登录前没有会话和可信用户身份，认证后再附加。Gate 根据独立的内部认证结果绑定用户，不解码业务 payload。
  - 提供“按会话主动推送”的入口，供 Node 调用。
- **Node**：
  - 维护逻辑服务的路由表，按数字路由和消息类型分发到 Handler。
  - 使用 Gate 传来的可信逻辑服务与 Codec 标识选择路由表和编码器，解码 payload，并把 Handler 结果编码为应答。
  - 登录 Handler 获得连接上下文，返回独立的认证结果；认证后的 Handler 获得会话、可信用户身份和主动推送能力。
  - 按目标会话描述中的 Codec 编码主动推送，支持同一逻辑服务的不同入口使用不同 Codec。
- **内部契约**：两个内部 Proto 服务，见 [ADR 0006](../../docs/adr/0006-gate-node-internal-contract.md)。分离部署走 Kratos gRPC；组合部署走本地调用，经过同一条中间件和错误链。
- **路由声明与生成器**：
  - 自定义方法选项声明请求、通知和登录请求的编号与类型，归属由所在 service 确定；主动推送消息的选项同时声明编号和所属 service 的全限定名，见 [ADR 0003](../../docs/adr/0003-numeric-route-per-logical-service.md)。
  - 生成器以 Buf 插件形式接入现有 `make api`，产出 Handler 接口、注册代码、Go 客户端调用和类型化推送分发代码。
  - 同一逻辑服务内编号重复、推送归属缺失或引用的 service 不存在时，生成失败。
- **Go 参考客户端**：
  - 连接、登录、心跳；
  - 请求与应答的 RequestID 关联；
  - 通知发送；
  - 由生成代码解码并调用类型化主动推送回调，业务调用方不手写编号和解码；
  - 把失败应答还原为 Kratos 错误。
- **示例应用**：一个逻辑服务，包含登录、一个请求、一个通知和一个业务触发的主动推送，提供组合部署与分离部署两种组装方式。
- **配置**：用 Kratos Config 加载强类型配置，覆盖入口、编码器、限制、超时、发送队列上限，以及下述连接和 Node 的在途执行上限。M1 不做热更新。
- **观测**：链路追踪从 Gate 开始，覆盖向 Node 的转交，复用 Kratos 的 tracing 中间件。指标不以用户、会话或 RequestID 为标签。

### 执行期限与资源上限

- Gate 为登录、业务请求和通知设置按入口配置的执行超时，以连接生命周期 Context 为父级，贯穿本地调用或 RPC 及 Handler。登录还受认证超时约束；连接关闭或服务停止时取消在途调用。
- 请求执行超时后返回明确的超时错误，迟到结果不再发送；通知不产生业务应答。Handler 应响应 Context 取消，框架不能强制终止不配合取消的业务代码，也不保证撤销已产生的副作用。
- Gate 限制每条连接的在途转交数量，Node 限制实例内正在执行的 Handler 总数；登录、业务请求和通知都计入上限，心跳由 Gate 直接处理。上限必须为正值，满额时不无界排队，也不创建等待名额的无限 goroutine。
- 达到执行上限时，请求返回明确的过载错误；通知无法接收时，Gate 断开该连接，不发送通知的业务应答。Node 的接收错误经内部调用返回 Gate，两种部署遵守同一策略。
- Node 的执行名额在 Handler 实际退出时才释放，不能仅因调用方超时便允许新的 Handler 越过执行上限。已取消调用不再进入尚未开始的 Handler；该上限不提供按用户串行或 M2 的 Keyed Executor 语义。
- Go 客户端在调用超时、取消或连接关闭时清理等待中的 RequestID，忽略迟到应答。单次客户端调用取消仅结束本地等待；M1 不新增取消消息，服务端执行受自己的期限和连接生命周期约束。超时或断连不自动重试请求。

## Testing Decisions

好的测试只经过模块对外的接缝验证外部行为，不断言内部结构。M1 有三个接缝。

### 接缝 A：客户端到入口的端到端测试

主要接缝。Go 参考客户端经真实的 TCP 或 WebSocket 连接示例应用。每个场景都在两种部署下运行：
- 组合部署：一个进程；
- 分离部署：测试进程内起独立的 Gate 与 Node，经本机真实 gRPC 通信。

覆盖以下场景：
- 认证前发普通请求会被拒绝；认证超时后连接断开。
- 未认证的登录不依赖会话 ID；失败登录不创建会话，登录超时或断连后的迟到成功结果不会完成绑定。
- 登录成功后，请求能收到对应 RequestID 的应答。
- Handler 返回 Kratos 错误时，客户端收到同一个 reason。
- 同一逻辑服务的两个入口分别使用 Protobuf 和 JSON，登录、请求、错误应答及主动推送均使用对应 Codec；Node 不支持的 Codec 被明确拒绝。
- 通知到达 Handler，客户端不会收到应答。
- 业务触发的主动推送能到达对应会话，生成的回调收到类型化消息，业务调用方不手写路由号或解码。
- 慢 Handler 达到执行期限后收到 Context 取消，客户端收到超时错误，迟到成功结果不再发送；连接关闭后，响应取消的 Handler 退出。
- 持续发送请求与通知时，单连接在途转交和 Node 实例的 Handler 数量不超过配置上限；请求收到过载错误，无法接收的通知使连接断开。超时但尚未退出的 Handler 仍占用 Node 执行名额。
- 客户端调用超时或取消后，等待项被清理，迟到应答不影响其他请求；连接关闭后所有等待调用结束，不自动重试。
- 心跳会被回复；空闲超时后连接断开。
- 超长包导致连接断开。
- 慢客户端的发送队列满后，连接被断开。
- 分离部署下，Node 下线后，相关会话被断开。

两种传输都要覆盖。

### 接缝 B：生成器

输入测试用的 proto，验证以下行为：
- 生成代码能编译；
- 生成代码注册的路由与声明一致；
- 同一逻辑服务内编号重复时，生成失败并报出冲突的编号。
- 同一 proto 文件的两个逻辑服务可使用相同的主动推送编号，生成的分发代码按各自所属服务解码到正确消息类型。
- 推送归属缺失或引用不存在的 service 时，生成失败；请求、通知与推送在同一服务内的编号冲突同样被拒绝。
- 生成的 Go 客户端同时提供类型化请求应答和主动推送回调，调用方不手写路由号或 payload 解码。

### 接缝 C：分帧解码

对 TCP 和 WebSocket 两种分帧，用 Go fuzz 输入任意字节，验证：
- 不 panic；
- 内存分配不超过最大包长；
- 合法信封经编码再解码后保持一致。

### 其他要求

- 测试之间相互独立，各自监听随机端口。
- 涉及并发的包运行 `go test -race`。
- 仓库目前没有可借鉴的测试先例，接缝 A 的测试工具由第一个用到它的任务建立。
- 任务 03 建立登录、Codec、执行期限与上限的组合部署验收；04 补推送的 Codec 验收；06 复用这些场景验证 RPC；07 生成类型化推送分发代码；08 完成两种传输与两种部署的整体验收。

## Out of Scope

- 在线索引、按用户推送和跨 Gate 投递，留到 M2。
- Etcd 分片归属、Fencing、Keyed Executor、故障接管和状态恢复，留到 M2。
- 会话恢复、连接代次、多连接登录策略和幂等扩展，留到 M2。
- 群组推送、再均衡、协调者、滚动升级和性能验收，留到 M3。
- 单连接访问多个逻辑服务，见 [ADR 0003](../../docs/adr/0003-numeric-route-per-logical-service.md)。
- 信封版本字段和客户端元数据，见 [ADR 0004](../../docs/adr/0004-client-protocol-envelope.md)。
- 按消息分级丢弃、配置热更新、KCP/QUIC、第二套 I/O 引擎，以及其他语言的正式 SDK。
- 房间、对战等游戏玩法。
