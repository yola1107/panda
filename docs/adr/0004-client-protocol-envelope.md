# 客户端协议的入口、信封与分帧

客户端协议发布后难以修改，因此首版先固定以下约定。

## 入口

TCP 每个逻辑服务一个监听端口；WebSocket 每个逻辑服务一个路径，多个路径可共用一个端口。
入口与逻辑服务的对应关系由配置确定，握手中不协商。
编码器按入口配置，如 Protobuf 或 JSON，不在消息中协商。
信封不含版本字段，协议升级通过新入口区分。

## 信封

所有消息类型使用同一个 13 字节固定头部，其后为 payload：

| 字段 | 长度 |
| --- | --- |
| 消息类型 | 1 字节 |
| 数字路由 | 4 字节 |
| RequestID | 4 字节 |
| 错误码 | 4 字节 |

不使用的字段填 0。信封不携带客户端元数据，链路追踪从 Gate 开始。

- 消息类型：请求、应答、主动推送、通知、心跳。
  两种传输使用同一种心跳消息，不依赖 WebSocket ping/pong，因为浏览器无法主动发送 ping。
  客户端定时发送心跳，Gate 直接回复，不转交 Node；空闲超时内未收到任何消息时，Gate 断开连接。
- 数字路由：uint32。请求、通知与主动推送共用逻辑服务的同一张路由表，每个编号只对应一种消息。
- RequestID：uint32，由客户端生成，在同一连接内递增且唯一，应答原样带回；其他消息类型填 0。
  RequestID 只关联请求与应答，不作为幂等键。
- 错误码：int32，应答使用，0 表示成功。
  失败应答的 payload 为 Kratos 错误结构（code、reason、message、metadata），按入口的编码器编码。
- 头部各字段采用大端序。

## 分帧

TCP 使用大端序 uint32 长度前缀；WebSocket 一个二进制消息即一帧，不加长度前缀。
最大包长按入口配置，默认 64 KiB，超出时断开连接。
