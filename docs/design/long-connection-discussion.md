核心定位：在 Kratos 微服务体系上补齐分布式长连接能力，而不是用数字路由重新组织整个后端。

| 维度 | 最终方向 |

## 三、全部问题、选项与关键点

### 起始需求

问题：你这次想讨论的需求是什么？

用户目标：做一个类似 Due 的分布式长连接服务器框架，底座基于 Kratos v3。

### 01～11｜底座、部署、通信与边界

#### 第01轮｜框架与 Kratos 的关系

问题：框架与 Kratos v3 应当是什么关系？

A. Kratos 增强型：围绕 Kratos Transport 扩展长连接。

B. Kratos 底座 + Due 架构：复用基础设施，自建长连接核心。

C. 独立框架 + Kratos 适配：Kratos 只是可替换集成层。

D. 尚未确定，先比较取舍。

选择与状态：B：Kratos 底座 + Due 架构。【已确认】

关键点：Kratos 承担应用生命周期、配置、服务发现、RPC 等基础能力；框架补齐 Gate、Node、Session 和长连接分发。 参考 Due 的能力与体验，不以复制 Due 全部组件为目标。后续明确取消 Mesh。 这是独立的 Go 长连接框架，不要求业务采用 Kratos 官方模板的目录与分层。

#### 第02轮｜组件部署模型

问题：Gate、Node、Mesh 是独立进程，还是允许同进程组合？

A. 严格分离，必须独立部署。

B. 模块化组合，可同进程或独立部署。

C. Gate 独立，Node/Mesh 灵活组合。

D. 暂不决定。

选择与状态：B：模块化组合部署。【已确认，范围已修订】

关键点：开发与测试可组合部署，生产按职责和负载拆分。 同一组件实现应支持组合和独立运行，不维护两套业务实现。

记录说明：第11轮取消 Mesh，因此最终组合对象主要是 Gate、Node 及可选功能组件。

#### 第03轮｜本地与远程通信

问题：同进程与跨进程调用采用什么模型？

A. 统一接口 + 本地快速调用。

B. 全部使用 RPC，包括同进程。

C. RPC + 异步消息总线。

D. 优先兼容 Due 原始通信体验。

选择与状态：A：统一接口 + 本地快速调用。【已确认】

关键点：同进程走本地调用，跨进程复用 Kratos RPC。 本地快速路径不能绕过必要的身份校验、中间件、Keyed Executor 和错误契约。 统一的是业务调用契约，不宣称本地与网络故障行为完全相同。

#### 第04轮｜路由与有状态亲和性

问题：消息如何找到正确的业务节点？

A. 无状态服务路由。

B. 服务路由 + 用户亲和性路由。

C. Actor / Entity 路由。

D. 完全参考 Due。

选择与状态：B：服务路由 + 用户亲和性路由。【已确认】

关键点：无状态请求可以按服务选择实例；有状态请求必须找到持有对应状态的合法 Owner。 绑定、解绑、迁移和故障恢复需要统一契约。 后续将 Ownership 收敛为按业务域划分的虚拟分片；普通 Kratos 微服务不因此强制接入分片。

#### 第05轮｜Session 与归属信息存储

问题：Session 和玩家归属信息如何存储？

A. 全局 Redis 管理。

B. 本地内存 + 分布式注册表。

C. 一致性哈希归属。

D. 只定义可插拔 Session/Registry 接口。

选择与状态：B：本地内存 + 分布式注册表。【已确认】

关键点：真实连接留在 Gate 本地，业务运行状态由相应 Node 管理。 分布式记录负责定位、绑定和归属协调；缓存通过版本及失效机制维护。 区分 Connection、Session、Presence 和 Ownership，不能用一份在线记录承担所有责任。

#### 第06轮｜多端连接与登录策略

问题：同一 UID 是否允许同时拥有多个 Session？

A. 全局单连接，新登录踢旧连接。

B. 多设备连接，支持 UID/设备/Session 投递。

C. 框架支持多连接，业务决定登录策略。

D. 仅管理 Session，UID 规则由业务全部实现。

选择与状态：C：框架支持多连接，业务决定登录策略。【已确认】

关键点：支持 UID 对应多个 Session，业务可选全局单连接、按设备类型单连接或多端在线。 框架负责执行绑定与冲突处理，业务负责准入及抢占决策。 并发登录需要原子绑定和旧连接失效机制，不能只靠先查后写。

#### 第07轮｜客户端 Transport

问题：首版支持哪些客户端传输协议？

A. 仅 TCP + WebSocket。

B. 可插拔 Transport，分阶段支持。

C. 首版同时支持 TCP、WebSocket、KCP、QUIC。

D. WebSocket 优先。

选择与状态：B：可插拔 Transport；首版 TCP/WebSocket，后续 KCP/QUIC。【已确认】

关键点：统一上层消息处理和 Session 使用方式，保留协议特有配置。 统一接口不代表不同协议具有完全相同的消息边界、连接与流语义。 KCP/QUIC 是后续扩展方向，不是首版交付要求。

#### 第08轮｜消息信封与编解码

问题：客户端消息采用什么协议与编解码架构？

A. Protobuf 优先，固定消息信封。

B. 统一消息信封 + 可插拔 Codec。

C. 完全参考 Due 消息协议。

D. 只处理原始字节，协议完全交给业务。

选择与状态：B：统一消息信封 + 可插拔 Codec。【已确认】

关键点：分别处理 Transport、Framing、Envelope 和 Payload Codec，避免互相耦合。 默认 Protobuf，允许 JSON 或自定义消息体编码。 Route、RequestID、消息类型与 Payload 的角色分开；精确字段、位宽和帧格式尚待制定。

#### 第09轮｜交互模式

问题：框架原生支持哪些消息交互？

A. Request/Response + Push。

B. Request/Response + Push + Notify。

C. 再内置 Pub/Sub、Stream、ACK、离线消息等完整能力。

D. 核心只收发消息，交互模式全部插件化。

选择与状态：B：Request/Response + Push + Notify。【已确认】

关键点：Request/Response 使用请求关联、超时和统一错误处理；Push 支持服务端主动发送。 Notify 是不要求业务响应的单向通知，不等于可靠消息。 节点间普通业务调用仍采用 Kratos RPC；不要求全部包装成数字路由通知。

#### 第10轮｜服务发现与在线索引

问题：Service Registry 与 Presence Registry 如何组织？

A. 全部复用 Kratos Registry。

B. 分离 Service Registry 与 Presence Registry。

C. 自建统一分布式元数据中心。

D. 分离接口，统一使用 Redis 后端。

选择与状态：B：分离 Service Registry 与 Presence Registry。【已确认】

关键点：服务注册发现复用 Kratos；在线索引使用独立的数据模型和生命周期。 注册表用于定位与协调，不是玩家业务状态数据库。 第34轮进一步拆分：Redis 负责 Presence，Etcd 负责 Ownership；不再将节点归属混在在线状态里。

#### 第11轮｜Mesh 是否必要

问题：在已有 Kratos RPC 和服务发现时，还需要 Mesh 吗？

A. 独立 Mesh 服务，跨节点消息统一中转。

B. 不需要 Mesh，直接使用 Kratos RPC。

C. 逻辑 Mesh 抽象，默认直连。

D. 直连与独立 Mesh Proxy 混合。

选择与状态：B：不需要 Mesh，直接使用 Kratos RPC。【已确认】

关键点：取消独立 Mesh 服务，也不把“逻辑 Mesh”作为必需框架层。 必要的长连接路由、归属查询和投递适配不等于重建通用服务通信平台。 第39轮的协调模块只管理分片计划，不转发业务流量，不是 Mesh。

#### 第13轮｜Handler 上下文与 Session API

问题：业务 Handler 如何获得会话信息并发送消息？

A. Context 直接携带可操作的完整 Session。

B. Kratos 风格 Context + 独立 Session API。

选择与状态：B：Kratos 风格 Context + 独立 Session API。【已确认】

关键点：Handler 使用 context.Context；通过独立会话管理和发送 API 执行绑定、推送等操作。 业务 Handler 不直接持有 Gate 的 TCP/WebSocket 连接。 跨进程只传递可信身份与会话描述，不伪装成能够跨进程访问的本地连接对象。

记录说明：原对话在 B 方案说明中截断；未展示的其他选项不补写。

#### 第14轮｜认证与绑定的责任

问题：身份认证和 Session 绑定由谁负责？

A. Gate 负责认证与绑定。

B. Gate 管连接，Node 管认证决策。

C. 强制独立 Auth 服务。

D. 全部交由可插拔认证流水线决定。

选择与状态：B：Gate 管连接，Node 管认证决策。【已确认】

关键点：Gate 管连接、心跳、协议与基础限流；Node 决定身份验证、业务授权和登录策略。 SessionManager 执行绑定、解绑与抢占，Gate 执行发送和断开。 匿名连接只能调用允许匿名的路由；客户端不能直接声明可信 UID。

#### 第15轮｜断线重连

问题：客户端重连时是否恢复原逻辑 Session？

A. 断线即销毁，重连建立新 Session。

B. 限时 Session 恢复 + 连接代次。

C. 内置 ACK、消息缓存与重放的完整无缝恢复。

D. 核心只提供可插拔恢复接口。

选择与状态：B：限时 Session 恢复 + 连接代次。【已确认】

关键点：逻辑 Session 可在恢复窗口内保留，验证身份或恢复凭证后允许跨 Gate 重连。 原子更新绑定并使用 Connection Epoch/Generation 隔离旧连接；每个设备独立恢复。 Session 恢复不等于 Node 状态恢复，也不默认承诺补齐断线期间消息。

#### 第16轮｜Node 故障恢复

问题：Node 宕机后，框架负责恢复到什么程度？

A. 基础故障转移，业务自行恢复。

B. 自动路由转移 + 可插拔状态恢复。

C. 框架内置状态存储、快照和操作日志。

D. 主备 Node / 热状态复制。

选择与状态：B：自动路由转移 + 可插拔状态恢复。【已确认】

关键点：框架协调故障检测、Ownership 重新分配和恢复阶段；业务 Hook 加载持久化状态。 新 Owner 在对应状态恢复完成后才开放有状态请求。 不承诺找回旧 Node 尚未持久化的数据；关键写入需要资源端 Fencing 或等效保护。

#### 第17轮｜可靠性与幂等

问题：框架采用什么消息投递、重试和幂等模型？

关键点：M1 跑通端到端；M2 验证分布式正确性；M3 完成生产验收。 有界队列、大小限制、超时取消、资源释放、基础安全和观测从 M1 就开始。 开发里程碑完成不等于达到生产验收；不先堆大量接口与空实现。

#### 第43轮｜首个客户端与 SDK

问题：首版优先提供哪种客户端支持？

A. Go 参考客户端。

B. TypeScript/JavaScript WebSocket SDK。

C. Unity/C# SDK。

D. 对接已有客户端或其他技术栈。

选择与状态：A：Go 参考客户端，先验证框架。【已确认】

关键点：覆盖 TCP/WebSocket、登录、请求响应、推送和错误处理，用于示例、集成测试与压测。 M1 完成基础交互，M2 再加入自动重连与 Session 恢复。 首版不同时交付跨语言 SDK 全家桶，也不默认增加离线缓存和可靠重放。

#### 第44轮｜客户端路由标识

问题：客户端用什么标识定位长连接业务方法？

A. 稳定字符串路由。

B. 显式数字路由。

选择与状态：B：显式数字路由；补充要求：每个长连接逻辑服务独立编号。【已确认】

关键点：服务 A 的 1/2/3 与服务 B 的 1/2/3 可以完全不同，不要求跨服务全局唯一。 在同一逻辑服务内检查重复编号；组合部署不合并命名空间，扩容不改变编号含义。 Route、RequestID 和 IdempotencyKey 各司其职；普通 Kratos 微服务不分配长连接路由号。

记录说明：用户特别反对依靠全局唯一数字编号区分所有后端服务；后续澄清进一步限定数字路由只属于长连接协议。

## 四、后续澄清与推荐用法

### 澄清1：为什么还要分析服务范围？

用户提问：“我有个疑问，为啥要这样分析？”

澄清结论：服务 A 和服务 B 可以使用相同的数字编号。需要检查的只是收到消息时目标服务是否已经确定。如果端点、连接上下文或已有寻址机制已提供范围，直接复用；不能据此强行增加 ServiceID 或要求一服务一连接。

修正：将“服务内编号独立”“服务寻址”和“客户端连接模型”分开。先确认已有调用链缺什么，再补充机制，不把每个实现细节都扩成新的架构选择。

### 澄清2：是否只有长连接需要数字路由？

用户提问：“只有长链接需要路由号，其余都是 Kratos 的微服务吧？”

边界确认：数字路由只属于客户端与长连接服务的消息协议；普通账号、排行榜等服务通过自己的 Protobuf service/method 和类型化 Kratos RPC 交互，不分配另一套数字路由。

Gate→远程 Node 的内部转发 RPC 可以携带 Route、Payload 和可信 Session 上下文。这是运输长连接协议数据，不意味着所有普通服务都要实现 Handle(route, payload)。

Node 是承载长连接业务处理及可选有状态能力的逻辑组件，不是所有 Kratos 微服务的新称呼。普通微服务不强制引入 Session、Group、Keyed Executor 或分片 Ownership。

---

### 澄清3：推荐怎样实际使用？

用户提问：“所以你推荐怎么使用呢？”

推荐方案：入口先确定长连接逻辑服务，服务内部使用独立数字路由，Handler 再按需要调用普通 Kratos 微服务。该使用建议尚未被用户逐项正式确认，尤其不等于第45轮已选择 B。

```text
客户端 A → A 的长连接入口 → A 的 Node 集群 → A 的路由表
客户端 B → B 的长连接入口 → B 的 Node 集群 → B 的路由表

A/1、A/2、A/3 与 B/1、B/2、B/3 是两套独立契约。
A 的多个兼容实例共享 A 的契约，不为每个实例重新编号。
```

首版建议通过 TCP 端口、WebSocket 路径或接入配置建立服务范围，连接保存这一范围；不要求每条消息重复携带 ServiceID。入口可在同一 Gate 进程内隔离，也可独立部署。具体选哪种入口方式待确认。

```text
客户端 Route=2
  → Gate 解析信封并取得可信会话上下文
  → 在已经确定的服务范围内选择 Node
  → Node 在自己的路由表中找到 Handler
  → 身份/权限校验、Keyed Executor 与业务处理
  → 直接使用本地业务模块，或调用普通 Kratos RPC
  → 响应或经 Sender/Gate 推送给客户端
```

Gate 不维护“数字路由→全部后端微服务”的全局映射。无状态请求按规则选实例，有状态请求先确定分片 Owner；Handler 内部普通 RPC 不绕回数字路由平台。

业务开发建议：协议中显式标记数字路由，生成 Handler 接口、注册代码和 Go 客户端调用；业务通常调用 GetBag(...)，不手写数字2。此前示例 longconn.route 是拟议自定义扩展，不是已存在的 Kratos API，确切语法尚未定稿。

背包、商城、房间不必从一开始拆成独立微服务。可先作为 Node 内业务模块，确有独立扩容、复用或发布需求时再拆。

## 五、跨模块关键约束

### 01｜数字路由的边界

同一长连接逻辑服务内唯一，不同服务可以重复；共享一套协议的实例共用编号。数字路由不是服务发现，也不是全后端 RPC 标识。普通 Kratos 微服务不进入这张路由表。

### 02｜服务范围与入口

完整定位需要已有的服务上下文与服务内路由号，但不意味着必须增加一个线上的 ServiceID 字段。端点、连接绑定和显式服务字段的选择仍属第45轮未决项。

### 03｜会话与归属分离

Connection 是实际网络连接；Session 是可恢复的逻辑会话；Presence 是在线投递索引；Ownership 是有状态处理权。四者生命周期与一致性要求不同。

### 04｜两类代次不能混用

连接代次隔离旧连接和重复登录；Ownership 代次隔离旧状态拥有者。协调者命令还需自己的授权与阶段校验，不能靠一个全局 Epoch 模糊覆盖所有责任。

### 05｜存储权威明确

Redis 在线索引可存在短暂过时，不能据此授予写权限。Etcd 是分片归属权威；玩家业务数据由业务持久化。两后端间的更新需要可恢复流程，不假设单事务。

### 06｜外部写入需要真正隔离

更新 Owner 或在 RPC 上检查 Epoch，不自动阻止旧 Node 写数据库。关键业务写入必须由存储端验证 Fencing Token 或采用等效事务保护；具体方案仍待实现设计。

### 07｜分片不等于串行队列

按业务域确定虚拟分片归属，按 UID/RoomID 等业务 Key 执行串行。首版不支持单实体覆盖归属，也不在扩容时直接改分片数和哈希规则。

### 08｜超时与幂等

超时可能意味着结果未知，而不是业务未执行。无幂等保障的副作用请求不自动重放；去重键、请求关联 ID 与数字路由各自独立。

### 09｜发送与送达分离

服务端接受消息、写入网络连接、客户端收到以及客户端处理完成，是不同状态。首版基础 Push/Notify 不默认提供离线可靠送达或通用 Exactly-Once。

### 10｜本地路径不绕过契约

同进程优化仍进入共同的校验、中间件、调度、错误和观测链。不能让组合部署获得额外权限，或让分离部署才暴露并发问题。

### 11｜恢复不等于热复制

Session 恢复不恢复旧 Node 内存；新 Owner 只能加载可用的持久化业务状态。首版迁移按摘流、安全切换、恢复实现，不承诺内存热复制或零业务中断。

### 12｜故障接管与再均衡分开

节点故障按既定规则自动接管；健康节点之间的扩容迁移先形成计划，经明确触发后分批执行。已切换的归属通过新迁移纠正，不直接回写旧 Owner。

### 13｜协调者不是数据中转

轻量 Coordinator 只管理归属和迁移计划，不负责转发每条消息。计划记录不能随领导权租约一起消失，旧协调者的延迟命令也必须可拒绝。

### 14｜过载保护不能延后

连接缓冲、执行队列、全局并发、路由限制和消息大小都有界。关键消息不能静默丢弃，慢客户端不能拖垮 Gate，迁移期间不靠无限缓存隐藏不可用。

### 15｜安全与可观测性

认证、授权、服务间信任和恢复凭证属于独立安全边界；代次不是认证。遥测避免 UID 等高基数标签，不逐条强制追踪心跳与高频推送。

### 16｜模块化不是重新造框架

继续使用 Kratos App 和显式依赖注入；不引入第二套 App、通用反射容器、强制 Actor 系统、动态插件加载器或覆盖所有微服务的数字路由层。

### 17｜正确性与性能分别验收

1万连接、1,000～5,000条/秒是待验证目标；旧 Owner 非法写入、重复关键操作或越权发生时，即使吞吐达标也不能通过生产验收。
